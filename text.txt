# 1. Главная цель

Нужно создать интерактивный AI-симулятор, в котором пользователь выступает в роли акима/городского управленца.

У всех пользователей одинаковые:

* исходные данные города;
* виртуальный бюджет;
* каталог мероприятий.

Пользователь обязан принять **ровно 5 управленческих решений**.

Каждое решение относится к одному из направлений:

1. транспорт;
2. экология/озеленение;
3. социальная инфраструктура;
4. безопасность;
5. городские сервисы.

После выбора решений система должна:

* проверить валидность сценария;
* проверить бюджет;
* применить эффекты выбранных мероприятий;
* учесть лаг реализации;
* учесть синергии;
* учесть несовместимости;
* пересчитать показатели районов;
* рассчитать Astana Quality of Life Score;
* показать изменение относительно baseline;
* показать, какие районы и показатели улучшились;
* выявить слабые места;
* показать вклад решений;
* передать уже рассчитанные данные AI-модулю;
* получить понятное управленческое объяснение;
* дать рекомендации по улучшению сценария.

**LLM никогда не рассчитывает Score самостоятельно.**

Все числа рассчитывает только deterministic simulation engine.

LLM получает готовый JSON с результатами и только интерпретирует его.

# 11. Синергии

Синергии применяются после обычных эффектов мероприятий.

Они НЕ масштабируются лагом.

## M1 + M2

Если выбраны обе меры:

T1 +2

только в районе, выбранном для M1.

## M10 + M12

Если выбраны обе меры:

B1 +2

только в районе M10.

## M5 + M6

Если выбраны обе меры:

E2 +2

только в районе M5.

Синергия должна отображаться отдельно от обычных эффектов в calculation breakdown.

# 12. Несовместимости

## M1 и M3

Нельзя выбрать одновременно вообще, независимо от районов.

Либо BRT, либо LRT.

## M4 и M7

Можно использовать обе меры в сценарии только если они назначены разным районам.

В одном и том же районе M4 + M7 запрещены.

Причина:

«Конфликт за городской участок.»

## M5 и M13

Можно использовать обе меры только в разных районах.

В одном районе запрещены.

Причина:

«Дублирование инфраструктурной программы.»

# 14. Calculation Engine

Вынеси calculation engine отдельно от API views и Django ORM.

Например:

backend/apps/simulator/domain/
engine.py
validator.py
scoring.py
optimizer.py
entities.py

Engine должен быть максимально чистым и unit-testable.

## Шаг 1 — baseline

Создать копию исходных показателей.

Никогда не мутировать глобальный dataset.

## Шаг 2 — обычные эффекты

Для каждого мероприятия:

factor = (8 - lag) / 8

effect_realized = effect_full × factor

District measure применяется только к указанному району.

City measure применяется ко всем пяти районам.

## Шаг 3 — синергии

Применить фиксированные synergy bonuses.

## Шаг 4 — clipping

Каждый показатель ограничить:

0 ≤ indicator ≤ 100

Использовать:

clip(value, 0, 100)

## Шаг 5 — District Score

Для района d:

D_d =
0.10*T1 +
0.10*T2 +
0.09*E1 +
0.11*E2 +
0.11*S1 +
0.11*S2 +
0.09*B1 +
0.09*B2 +
0.10*C1 +
0.10*C2

## Шаг 6 — population-weighted city average

D_avg = Σ population_share_d × D_d

## Шаг 7 — weakest district

D_min = min(D_d)

## Шаг 8 — critical indicators

N_crit — число комбинаций:

district × indicator

для которых итоговый показатель:

indicator < 40

СТРОГО меньше 40.

Значение ровно 40 НЕ является critical.

## Шаг 9 — Final Score

Score =

0.7 × D_avg
+
0.3 × D_min
-----------

1.0 × N_crit

Никаких дополнительных штрафов или бонусов не вводить.

Не нормализовать формулу.

# 20. Deterministic Recommendation Engine

AI не должен сам придумывать «математически лучший вариант».

Создай deterministic improvement engine.

Для текущего сценария попробуй допустимые локальные изменения:

* заменить одно мероприятие другим;
* для district measure поменять район.

Каждый candidate:

1. проходит validator;
2. пересчитывается simulation engine;
3. сравнивается с текущим Score.

Верни несколько лучших **валидных альтернатив**.

Например:

{
"recommendations": [
{
"change": "...",
"score": 57.12,
"delta_vs_current": 0.58,
"reason_data": {...}
}
]
}

AI получает уже эти рассчитанные candidates и может объяснить их человеческим языком.

# 22. AI Agents

Реализуй несколько специализированных analytical agents.

## Equity Agent

Получает готовые данные simulation result.

Анализирует:

* weakest district;
* разрыв между районами;
* critical indicators;
* насколько сценарий помогает Нуре и другим слабым районам.

Не пересчитывает значения.

## Trade-off Agent

Объясняет:

* что улучшилось;
* какими компромиссами это достигнуто;
* какие направления получили мало внимания;
* отрицательные эффекты вроде M11 → T1 -2.

## Risk Agent

Выделяет:

* показатели около critical threshold;
* районы с сохраняющимися проблемами;
* большую концентрацию бюджета;
* лаги долгосрочных проектов.

Не выдумывает новые риски, не содержащиеся в данных.

## Strategy Agent

Получает deterministic candidate recommendations.

Объясняет:

* какая замена может улучшить сценарий;
* какой район можно поддержать;
* почему calculated alternative отличается.

Никаких придуманных цифр.

## Executive Synthesizer

Получает выводы предыдущих агентов и составляет финальную записку акиму.

Формат:

* Итог;
* Что сработало;
* Главные компромиссы;
* Риски;
* Что можно изменить;
* Короткий вывод.

Ответ должен быть на русском языке.

Не делай текст чрезмерно длинным.

# 23. AI safety against hallucinated numbers

В system prompt AI-модуля обязательно объясни:

* нельзя самостоятельно вычислять Score;
* нельзя менять предоставленные числа;
* нельзя придумывать мероприятия;
* нельзя придумывать районы;
* нельзя придумывать эффекты;
* все числа считаются trusted deterministic engine;
* AI должен интерпретировать только переданный structured JSON.

Рекомендации AI должны ссылаться только на реальные calculated candidates.

# 53. Important mathematical rules

Особое внимание:

1. лаг применяется только к обычным effects;
2. synergy лагом НЕ масштабируется;
3. effects суммируются;
4. затем clipping;
5. N_crit рассчитывается ПОСЛЕ всех effects и clipping;
6. district weights = именно указанные веса;
7. population weights = именно указанные доли;
8. remaining budget не влияет на Score;
9. порядок decisions не влияет;
10. invalid scenario вообще не получает Score;
11. значения должны храниться с нормальной precision;
12. округление использовать только для display.

Не округлять промежуточные эффекты до целого.
